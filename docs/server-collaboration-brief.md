# 요니버스 빼빼로데이 웹 서버 개발 협업 전달서

2026년 10월 29일 기준 · 기획자 겸 디자이너·퍼블리셔 → 서버 개발 협업자

개인 링크로 디지털 빼빼로와 편지를 주고받고, 11/11에 990원을 한 번 결제해 받은 선물 전체를 확인하는 시즌성 웹서비스입니다. 이벤트 결제 성과와 함께 요니버스 앱 신규 가입 유입을 실험합니다. 아래 확정 정책을 기준으로 서버 개발 범위와 일정을 검토하고, 미정 사항은 함께 결정하려고 합니다.

- 배포 목표: 2026년 11월 4일. PC·모바일 모두 지원합니다.
- 현재 상태: 기획 및 플로우차트 정리 단계입니다. 이 프로젝트에는 실제 웹 코드·서버·결제 연동이 아직 없습니다.

## 역할과 협업 범위

| 담당 | 범위 |
| --- | --- |
| 기획자 겸 디자이너·퍼블리셔 | 서비스 정책, 화면 흐름, PC·모바일 디자인, 커스텀 에셋과 문구, 퍼블리싱 |
| 서버 개발 협업자에게 요청하는 범위 | 카카오 인증, 계정·공간·선물 저장, 중복 전송 방지, 열람 권한, 결제 연동, 이메일 설정·발송, 마감 처리, 가입 유입 측정 연동 검토 |
| 함께 정할 범위 | 프런트 API 연동과 상태 처리 담당, 웹·서버 배포 담당, 기존 앱 수정 담당, 통합 테스트와 운영 담당 |

기획자가 퍼블리싱을 맡는다는 이유로 로그인·결제 SDK와 API 연동까지 담당하는 것으로 전제하지 않습니다. 프런트 연동 담당을 먼저 정하고, 요청·응답 형식과 오류 상태를 합의해야 합니다. 기존에 언급한 약 2일의 작업 가능 시간은 전체 서버 개발 일정 확약이 아니며, 서버 공수와 외부 서비스 승인 기간은 별도 산정이 필요합니다.

## 서비스 흐름

1. 카카오 로그인 후 이름을 입력해 개인 공간과 공유 링크를 만듭니다.
2. 지인은 링크로 방문해 빼빼로를 꾸미고 포장·카드·편지를 작성합니다. 발신자 표시용 인스타그램 아이디도 직접 입력합니다.
3. 완성본 확인 후 필요 시 카카오 로그인합니다. 작성 내용은 로그인 뒤에도 유지하도록 설계합니다.
4. 서버에서 마감 여부와 동일 수신자 발송 이력을 확인하고 선물을 저장합니다.
5. 공간 주인은 결제 전에는 선물이 있는지 없는지만 확인합니다. 알림을 원하면 이메일을 설정합니다.
6. 11/11 이메일을 통해 재방문하거나 직접 방문합니다. 990원 결제 완료 후 받은 개수·발신자·선물·편지를 열람합니다.
7. 결제 후 추가로 도착한 선물도 재결제 없이 모두 열람합니다.

꾸미기는 베이킹 게임이 아닌 간단한 선택형 경험입니다. 막대·하트 모양, 코팅, 토핑, 드리즐, 포장, 리본, 카드 옵션과 최대 200자 편지를 사용합니다. 정확한 옵션 목록은 상세 기획 문서를 따르며 복수 토핑·자유 배치 여부는 미정입니다. 저장 형식은 최종 옵션 구성과 함께 합의합니다.

## 확정 정책

### 전송과 본인 식별

- 선물 보내기는 무료이며 하루 제작·발송 제한은 없습니다.
- 행사 기간 동안 한 발신자가 같은 수신자에게 보낼 수 있는 선물은 1개입니다. 날짜가 바뀌어도 초기화되지 않습니다.
- 판별 기준은 행사 내 발신자 로그인 유저 ID와 수신자 유저 ID입니다. 이메일이나 직접 입력한 인스타그램 아이디로 중복 판별하지 않습니다.
- 인스타그램 아이디는 소유 인증하지 않는 표시 정보입니다. 실제 계정 주인임을 보장하지 않습니다.
- 실패한 요청은 재시도할 수 있어야 하며, 연속 클릭·동시 요청·응답 유실로 선물이 중복 생성되면 안 됩니다.

### 결제와 공개 범위

990원 1회 결제로 이번 행사에서 받은 모든 빼빼로를 열람합니다. 결제 전 도착분과 결제 후 추가 도착분을 모두 포함하며 재결제는 없습니다.

| 조회자와 상태 | 공개 가능한 정보 |
| --- | --- |
| 공간 주인, 미결제 | 선물 있음·없음만 |
| 공간 주인, 결제 완료 | 받은 개수, 발신자가 입력한 인스타그램 아이디, 꾸민 선물, 카드·편지 |
| 다른 방문자 | 공간의 공개 정보만. 선물 수신 여부·개수·내용은 비공개 |

화면에서 가리기만 해서는 안 됩니다. 서버 응답에서도 미결제자에게 선물 개수·발신자·내용을 보내지 않아야 합니다. 선물 상세와 관련 파일도 본인의 열람 권한을 확인해야 합니다. 방문자 화면의 쌓인 선물이나 외관 변화로 수신 여부가 드러나지 않도록 합니다.

### 일정과 마감

모든 서비스 일정은 한국 시간입니다. 서버가 시간을 판정하며, 사용자 기기의 시간을 신뢰하지 않습니다.

| 기능 | 허용 기간 |
| --- | --- |
| 선물 보내기 | 서비스 오픈부터 2026년 11월 12일 00:00 직전까지 |
| 신규 결제 | 2026년 11월 11일 00:00 이상, 11월 12일 00:00 미만 |
| 결제 완료자의 열람 | 결제 완료부터 가능. 열람 종료일은 미정 |

사용자에게는 ‘11/11 밤 11:59까지 보내기·결제 가능’으로 안내합니다. 11/12 00:00부터 신규 전송·결제를 차단합니다. 꾸미기를 마감 전에 시작해도 전송 요청이 마감 후라면 보낼 수 없습니다. 마감 후 미결제자는 결제해 선물을 열 수 없습니다.

마감 전에 시작했지만 이후 승인되는 진행 중 결제의 처리 기준은 아직 미정입니다. 결제 생성 시각·결제사 승인 시각·서버 통지 도착 시각을 구분해 합의해야 하며, 늦은 통지를 무조건 결제 실패로 처리해서는 안 됩니다.

## 카카오 로그인과 이메일 알림

로그인은 카카오로 합니다. 알림은 이메일로 보내며 카카오 채널 추가나 SMS는 현재 필수 범위가 아닙니다.

| 사용자 선택 또는 상태 | 처리 |
| --- | --- |
| 알림 수신 동의 안 함 | 알림 미발송. 서비스 이용은 가능 |
| 알림 수신 동의 + ‘카카오 이메일 사용’ 체크 | 제공된 유효·인증 이메일을 표시하고 알림 주소로 사용 |
| 알림 수신 동의 + 체크 해제 | 별도 이메일 입력·인증 후 저장 |
| 카카오 이메일 없음 또는 유효·인증 상태 확인 불가 | 직접 입력·인증 흐름으로 전환 |

‘카카오 이메일 사용’은 주소 선택이고, 알림 수신 동의와 별개입니다. 카카오 이메일 제공 동의를 서비스 알림 동의로 취급하지 않습니다. 다른 이메일을 입력해도 로그인 계정은 유지합니다. 알림 주소 변경과 수신 해제를 제공하며 직접 입력·변경 주소를 인증합니다. 인증 방식과 체크 초기값은 미정입니다.

11/11 발송 이메일에는 내 공간으로 돌아오는 링크를 넣습니다. 비공개인 선물 개수·발신자·편지 내용은 담지 않습니다. 링크 방문 뒤 로그인과 열람 권한을 확인합니다.

발송 대상은 ‘수신 동의 + 사용 가능한 주소 + 선물 있음 + 미결제’ 조건을 제안한 상태입니다. 발송 시각·횟수·재알림 여부와 함께 확정해야 합니다. 발송 직전에 최신 동의·주소 상태를 확인하고, 발송 기록과 중복 방지·실패 재시도를 처리하는 방향으로 검토합니다.

### 기존 요니버스 연동 검토

기존 요니버스 앱과 서버에는 카카오 로그인 구현이 있습니다. 같은 카카오 앱 설정을 재사용할 수 있는지 관리자 콘솔에서 웹 도메인·로그인 복귀 주소·이메일 동의 항목을 확인해야 합니다. 웹 로그인 연동 완료나 기존 계정 통합이 확정된 상태는 아닙니다.

기존 서버가 이메일을 받아오는 것과 유효·인증 상태를 확인하는 것은 구분해야 합니다. 카카오 설정 재사용, 회원 데이터 연결, 이벤트 데이터 저장 위치는 별도 협의 대상입니다. 키와 비밀값은 문서에 포함하지 않고 배포 환경에서 관리합니다.

## 상시 홍보와 앱 가입 유입 측정

요니버스 앱과 요매거진 인스타그램 링크를 작은 비중으로 상시 노출합니다. 특정 행동 완료 시점에만 나타나는 홍보가 아닙니다. 위치·형태는 디자인 단계에서 정합니다.

측정할 항목은 이벤트 방문자 수, 앱 이동 클릭 수, 인스타그램 이동 클릭 수, 이벤트를 통한 실제 앱 신규 가입자 수와 가입 전환율입니다. 웹 카카오 로그인이나 앱 링크 클릭을 앱 신규 가입으로 집계하지 않습니다. 기존 앱 회원 재방문은 별도 집계하고, 신규 가입자는 중복 제외합니다.

앱 설치 전후 유입 정보를 연결하는 방법과 실제 가입 완료를 확인할 수 있는 앱·서버 연동이 필요합니다. 신규 가입 인정 시점, 집계 기간, 방문자 중복 제거 기준을 합의해야 합니다. 인스타 링크 클릭은 팔로우 완료를 의미하지 않습니다.

## 서버 설계 협의 초안

아래는 정책 구현을 위한 논리적 범위입니다. 테이블명·API 경로·기술 스택을 확정하는 명세가 아닙니다.

| 영역 | 필요한 데이터 또는 처리 |
| --- | --- |
| 행사 | 식별자, 전송 마감, 결제 시작·마감, 가격, 별도 열람 종료 설정 |
| 회원과 공간 | 카카오 사용자 연결, 공간 주인, 공개 이름, 고유 공유 링크 |
| 선물 | 행사, 발신자·수신자, 커스텀 옵션, 카드·편지, 입력 인스타 ID, 생성 시각 |
| 주문과 열람 권한 | 주문·결제 식별자, 금액·상태·승인 시각, 행사와 소유자 기준 열람 권한 |
| 알림 | 수신 동의와 변경 시각, 선택 주소·출처, 인증 상태, 발송·재시도 기록 |
| 유입 측정 | 이벤트 유입 식별 정보, 앱·인스타 클릭, 앱 신규 가입과 연결할 정보 |

선물은 행사·발신자·수신자 조합의 중복을 저장 단계에서도 막는 방안을 권장합니다. 결제 권한은 구매 시점의 선물 목록이 아닌 행사·소유자에 부여해야 이후 수신분도 포함할 수 있습니다. 결제 성공은 브라우저 화면만으로 판단하지 않고 서버에서 결제사 결과·금액·주문 소유자를 확인합니다. 같은 결과가 반복 전달돼도 한 번만 반영해야 합니다.

프런트와 합의할 API 범위는 로그인·세션, 공간 생성·조회, 전송 가능 여부와 실제 전송, 소유자 수신 상태·목록·상세, 주문 생성·결제 상태, 알림 설정·이메일 인증입니다. 사전 전송 가능 여부 조회와 관계없이 실제 저장 시점에 마감·중복·수신자 유효성을 다시 검증해야 합니다.

화면에서 구분할 상태는 로그인 필요, 이미 보낸 상대, 전송 마감, 결제 시작 전·마감 후, 결제 확인 중·실패·취소, 열람 권한 없음, 이메일 인증 실패입니다. 상태 이름과 응답 규격은 함께 정합니다.
